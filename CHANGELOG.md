# Changelog

### [2026-08-23 01:10] Added

**Tech:** `server/store.js` — `createStore(dataDir) → { read, write, init, backup }`; `tests/store.test.js`
**Dev:** The only filesystem-touching module in the project. `write()` serialises to JSON before any I/O, then writes to `<file>.tmp` and `rename`s over the target, so a value that fails to serialise (e.g. a circular reference) never touches disk and a crash mid-write can't leave a half-written `ledger.json`. `COLLECTIONS` is a hardcoded allow-list of the six collection names; an unknown name throws before any path is built, closing off path traversal via a crafted name. Fixed a real bug in the brief's reference `backup()`: its timestamp directory name was millisecond-resolution only, so two backups requested in the same millisecond would silently collide and the second would overwrite the first — confirmed by freezing `Date` in a test so both calls compute an identical stamp. Fixed by probing for an existing directory and appending a numeric suffix until the name is free.
**Plain:** Added the module that saves and loads all the app's data as JSON files, always safely (a crash can't corrupt your file) and always with a backup taken before anything is overwritten.
**Why:** Years of imported bank data live in these files, so a half-written file after a crash or two backups silently overwriting each other would mean losing history with no way back — this closes both gaps before anything else in the app is built on top of it.

### [2026-08-23 00:30] Fixed

**Tech:** `lib/csv-parse.js` — new `parseCsvWithLines(text) → {fields, line}[]`, with `parseCsv` reimplemented in terms of it; `lib/ingest.js` — `sniffFormat` call wrapped in try/catch, malformed rows now report the true physical line
**Dev:** Two defects on the import error path. First, `sniffFormat` throws when a file parses to a single row containing neither a date nor an amount — which includes a header-only CSV, i.e. a statement exported for a period with no transactions. Because the preview endpoint calls `ingest()` directly, that surfaced as a 500 rather than a readable message, violating the never-fatal contract. Caught inside `ingest` rather than at the HTTP layer, so preview and commit keep exactly one error behaviour. Second, reported line numbers were indexes into the parsed-rows array, so they drifted by one per preceding blank line and per newline embedded in a quoted field — sending the user to the wrong row of their own CSV. `parseCsvWithLines` now carries the 1-based physical line on which each record starts. `parseCsv`'s signature is unchanged so `format-sniff` and its tests are unaffected. Also: unmapped columns now report "no date/amount column could be identified" instead of the misleading `Unreadable date: ""`, and a zero amount in a positive-spend file no longer yields `-0`.
**Plain:** Uploading a statement with no transactions in it, or a file that isn't really a statement, now shows a clear "couldn't read this" message instead of crashing — and when a row can't be read, the line number points at the right row.
**Why:** An import that dies with a generic error tells you nothing about what went wrong, and a line number that quietly points two rows off is worse than no line number at all — you'd go looking at a perfectly good transaction and wonder what was wrong with it.

### [2026-08-22 21:15] Fixed

**Tech:** `lib/categorise.js` — `matchRule()`'s `contains` branch now tests `\b<escaped value>\b` (new `escapeRegex()` helper) against `subject` instead of `String.includes()`; `data/seed/rules.json` — the 9 rules converted to ad-hoc `regex` in the previous entry (`iga`, `aldi`, `agl`, `atm`, `bp`, `ola`, `shell`, `opal`, `dental`) are reverted back to plain `contains`, with `bp`/`ola` now written without their old trailing-space guard (`"bp "` → `"bp"`, `"ola "` → `"ola"`); `tests/categorise.test.js` — the reachability test's `coreLiteral()` special-casing removed, replaced by tagging each rule with its own array index as a stand-in `categoryId` and asking the real `matchRule()` which rule wins for that rule's own value
**Dev:** Re-review after the previous fix found five more of the same embedded-substring bug the first pass missed (`coles` inside "Nicoles Hairdressing", `target` inside "Targeting Solutions", `amazon` inside "Amazonite Crystals", `fruit` inside "Fruition Financial", `medical` inside "Non-Medical Homecare") — converting one offending value to `regex` at a time is whack-a-mole, and every future rule the user adds reopens the same hole. This is the structural fix: **`contains` now means "contains this word or phrase", not "contains this character sequence".** Every seed rule was written intending a whole-word/phrase match — none of them intend to match mid-word — so this is `contains` behaving as originally intended, not a special case bolted on top; the previous entry's per-token `regex` conversions are reverted because the mechanism that made them necessary no longer exists. `escapeRegex()` is required because several rule values contain literal `.` (`stan.com`, `apple.com`, `booking.com`, and `netflix` matched against `netflix.com`) which must match a literal dot, not "any character" — an unescaped value would silently become a much looser pattern. Of the five newly-reported cases, four are fixed by this change and verified against the live matcher; the fifth, `medical` inside "Non-Medical Homecare Services", is **not** the same bug and is not fixed, on purpose: a hyphen is not a `\w` character, so `\bmedical\b` is satisfied by "Non-Medical" exactly as it would be by "Non Medical" with a space — "Medical" genuinely is its own grammatical word there, just negated by a prefix. No token-boundary rule can generically distinguish an affirmed word from a negated one; a one-off pattern excluding "non-" would be exactly the whack-a-mole this fix moved away from. Documented as an accepted limitation (pinned by its own test) rather than silently left unverified or papered over with a special case. The reachability test's `coreLiteral()` helper (added to reason about mixed `contains`/`regex` seed rules) is now unneeded dead code, since every seed rule is `contains` again — replaced with a simpler and more robust technique that reuses the real `matchRule()` directly (tag each rule with its own index as its `categoryId`, then check that a rule's own value resolves to its own index) rather than re-deriving matching semantics by hand in the test.
**Plain:** Changed how the shop-name matching rules work under the hood so that a rule like "coles" only matches the actual word "Coles", never matches as a fragment buried inside an unrelated name like "Nicoles Hairdressing" or "Amazonite Crystals" — fixing that whole category of mistake at once instead of patching each example as it turns up.
**Why:** The first fix handled the specific examples found in review, but review found more of the same bug on the next pass, which is exactly what happens when you fix symptoms one at a time instead of the underlying rule — this closes the door on the entire class, including for any rule the user or a future review adds later, rather than needing another round of "just one more example."

**Tech:** `lib/categorise.js` — `matchRule(merchant, rules)`, `categoriseTransaction(txn, rules, merchantsWithPriorSpend)`; seed data at `data/seed/categories.json` (7 groups, 29 categories) and `data/seed/rules.json` (101 ordered merchant rules)

### [2026-08-22 19:50] Added

**Tech:** `lib/dedupe-hash.js` — `transactionId({ accountId, date, amount, rawDescription, occurrenceIndex })`, `assignOccurrenceIndexes(rows)`
**Dev:** `transactionId` joins the five fields with a separator and takes the first 16 hex chars of a SHA-256 digest; `amount` is normalised via `Number(amount).toFixed(2)` (with `-0.00` folded to `0.00`) so equivalent numeric representations — `-64.15` vs `-64.150`, or a float artifact like `0.1 + 0.2` — always hash the same. `assignOccurrenceIndexes` numbers each row by its position within its own duplicate group **in the file being imported** (grouped by accountId/date/amount/rawDescription), counting from 0 — not a counter against the existing ledger — which is what makes re-import idempotent: the same file always assigns the same indexes, so the same ids, so a re-import adds nothing, while two genuinely-identical same-day transactions (two Coles trips, two Myki top-ups) still get distinct ids via distinct indexes. Returns new row objects in a new array; does not mutate its input. Caveat carried from the design note: if the same transaction is split across two separate files that each contain only one half of what would have been a duplicate pair, both get `occurrenceIndex: 0` and one is treated as a duplicate on import — accepted as rare and preferable to the alternative of silently duplicating real spend, and always visible via the import summary's skipped-duplicate count. The plan's reference implementation had a literal syntax error (an unterminated string in `.join(`) — reimplemented cleanly with an explicit separator constant rather than copied as-is.
**Plain:** Added the code that gives every imported bank transaction a stable ID, so re-importing the same statement never creates duplicate entries, while two real separate purchases that happen to look identical (same day, same amount, same description) still both get kept.
**Why:** Bank statements get re-exported and re-imported over years of overlapping date ranges, and the ledger needs to just merge cleanly every time rather than the user having to manually spot and delete duplicate rows — or worse, having a genuine repeated purchase like a second Myki top-up silently dropped because it looked like a duplicate.

**Plain:** Closed the rest of the gap from the last fix: a payment-terminal reference code stuck onto a "Wdl" or "Direct Debit" prefix (not just the gateway-style prefixes already fixed) was still being shown as if it were the shop's name instead of being discarded.

**Plain:** Fixed four bugs in the code that cleans up bank-statement merchant names: it was wrongly blanking out real shop names like "7ELEVEN" and "13CABS", cutting off the last word of longer names like "The Royal Melbourne Hotel", collapsing genuinely repeated names like "Bar Bar" down to just "Bar", and could very rarely give a slightly different answer if run twice on its own output.

### [2026-08-22 18:10] Fixed

**Tech:** `lib/format-sniff.js` — `findBalancePair()` (new), `sniffFormat()`'s header/amount/description/account selection, `detectDateFormat()`, `parseAmount()`
**Dev:** Code review surfaced five real defects in the sniffing heuristics, each now covered by a dedicated test: (1) amount-vs-balance selection scored columns by share-of-negatives then mean-magnitude, so a credit-card layout (positive charges, negative running balance) and an overdrawn account (both columns negative, balance nearer zero) both picked the balance column as `mapping.amount` — fixed by trying the running-balance relation first (`balance[n] - balance[n+1] ≈ ±amount[n]` across consecutive sample rows, either row order, via new `findBalancePair()`), falling back to the old negShare/meanAbs scoring only when no pair fits a clear majority of rows; the stale comment describing "last numeric column" logic is corrected to match. (2) header detection only inspected column 0, so a layout with a leading non-date column (e.g. `Bank Account,Date,Narrative,Amount,Balance`) missed its header row entirely; now a row counts as a header only when no cell in it looks like a date or an amount, checked across every column, while the next row has at least one of each — and the previously-dead "header but no data rows" guard now actually fires, for a file that is a single header-shaped row with nothing below it. (3) `description` was chosen by longest average text, so a repeated long account name (e.g. "Joint Everyday Transaction Account") beat short merchant strings and would have fed the account name into merchant normalisation for every row; now chosen by highest cardinality (merchant text is close to unique per row) with average length only as a tie-break, and `account` is assigned only when a remaining column's cardinality is genuinely low relative to the sample — left `null` rather than guessed when only one candidate column remains and there is nothing to compare it against. (4) a date column mixing `22/08/2026` and `08/22/2026` (self-contradictory — no single DD/MM or MM/DD reading fits both) fell through to `dateFormatConfidence: 'high'`; now returns `'low'` when both position-over-12 signals fire. (5) `parseAmount('1.404,01')` and `parseAmount('1 404,01')` silently returned values 100x too large (European decimal-comma and space-grouped forms misread as US thousands-grouping); now any comma usage is validated against strict US-style grouping (`\d{1,3}(,\d{3})+` before an optional `.` decimal) and rejected as `null` otherwise. European and space-grouped amount formats remain unsupported by design — the fix is refusing to guess, not adding support.
**Plain:** Fixed five cases where the CSV-format guesser would have gotten it wrong in ways that are hard to notice: picking the running balance instead of the actual transaction amount on credit-card and overdrawn-account exports, missing the header row on layouts that don't start with the date, mislabelling an account name as the transaction description, calling a self-contradictory date column "confident" when it isn't, and silently turning a European-style amount like 1.404,01 into a number 100 times too big instead of refusing to guess.

### [2026-08-22 16:20] Fixed

**Tech:** `lib/csv-parse.js` — bare mid-field quotes now literal, leading UTF-8 BOM stripped
**Dev:** Code review across 17 inputs found two real-world breakages: (1) a stray `"` inside an unquoted field (e.g. `a"b,c`) flipped the parser into quoted mode, silently swallowing the following comma and dropping a column — now a `"` only opens quoted mode when it's the first character of a field (`field === ''`), matching Excel; any other `"` is appended literally.
