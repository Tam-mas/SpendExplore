# Changelog

### [2026-08-22 18:10] Fixed

**Tech:** `lib/format-sniff.js` — `findBalancePair()` (new), `sniffFormat()`'s header/amount/description/account selection, `detectDateFormat()`, `parseAmount()`
**Dev:** Code review surfaced five real defects in the sniffing heuristics, each now covered by a dedicated test: (1) amount-vs-balance selection scored columns by share-of-negatives then mean-magnitude, so a credit-card layout (positive charges, negative running balance) and an overdrawn account (both columns negative, balance nearer zero) both picked the balance column as `mapping.amount` — fixed by trying the running-balance relation first (`balance[n] - balance[n+1] ≈ ±amount[n]` across consecutive sample rows, either row order, via new `findBalancePair()`), falling back to the old negShare/meanAbs scoring only when no pair fits a clear majority of rows; the stale comment describing "last numeric column" logic is corrected to match. (2) header detection only inspected column 0, so a layout with a leading non-date column (e.g. `Bank Account,Date,Narrative,Amount,Balance`) missed its header row entirely; now a row counts as a header only when no cell in it looks like a date or an amount, checked across every column, while the next row has at least one of each — and the previously-dead "header but no data rows" guard now actually fires, for a file that is a single header-shaped row with nothing below it. (3) `description` was chosen by longest average text, so a repeated long account name (e.g. "Joint Everyday Transaction Account") beat short merchant strings and would have fed the account name into merchant normalisation for every row; now chosen by highest cardinality (merchant text is close to unique per row) with average length only as a tie-break, and `account` is assigned only when a remaining column's cardinality is genuinely low relative to the sample — left `null` rather than guessed when only one candidate column remains and there is nothing to compare it against. (4) a date column mixing `22/08/2026` and `08/22/2026` (self-contradictory — no single DD/MM or MM/DD reading fits both) fell through to `dateFormatConfidence: 'high'`; now returns `'low'` when both position-over-12 signals fire. (5) `parseAmount('1.404,01')` and `parseAmount('1 404,01')` silently returned values 100x too large (European decimal-comma and space-grouped forms misread as US thousands-grouping); now any comma usage is validated against strict US-style grouping (`\d{1,3}(,\d{3})+` before an optional `.` decimal) and rejected as `null` otherwise. European and space-grouped amount formats remain unsupported by design — the fix is refusing to guess, not adding support.
**Plain:** Fixed five cases where the CSV-format guesser would have gotten it wrong in ways that are hard to notice: picking the running balance instead of the actual transaction amount on credit-card and overdrawn-account exports, missing the header row on layouts that don't start with the date, mislabelling an account name as the transaction description, calling a self-contradictory date column "confident" when it isn't, and silently turning a European-style amount like 1.404,01 into a number 100 times too big instead of refusing to guess.
**Why:** These are exactly the "looks fine until you check the numbers" bugs the whole module exists to prevent — a wrong balance-vs-amount pick or a misread European amount would have quietly fed wrong numbers into every chart, and nobody would think to double-check a number that looks plausible.

### [2026-08-22 17:05] Added

**Tech:** `lib/format-sniff.js` — `sniffFormat(rows)`, `parseDate(value, dateFormat)`, `parseAmount(value)`
**Dev:** Infers column layout, date format and sign convention from sampled rows (first 50) rather than requiring a config file per bank — column roles are scored from the data itself, not hard-coded positions or header names. The date column is whichever one matches a date pattern in ≥80% of sampled values. Day/month order is genuinely ambiguous when no sampled date has a day above 12 (`05/08/2026` could be 5 Aug or 8 May) — in that case the function still returns a best guess (Australian `DD/MM/YYYY`) but sets `dateFormatConfidence: 'low'` so the import preview can warn the user instead of silently picking a side. `sniffFormat` never applies its guess; it only proposes one, and every field of the result is a hint for the import preview to confirm. (The original amount-vs-balance and description-vs-account column heuristics shipped here had real bugs on non-CommBank layouts — corrected in the Fixed entry above, which also documents the current mechanism for both.)
**Plain:** Added the code that looks at an imported bank CSV and guesses which column is the date, which is the amount, and whether spending shows up as negative or positive numbers — a guess the app will show you before importing anything.
**Why:** Every bank exports its CSV differently, and if the app guessed wrong about which number is money spent vs. money received, every chart would flip upside down without any obvious sign something was wrong — this makes that guess visible and checkable instead of silent.

### [2026-08-22 16:20] Fixed

**Tech:** `lib/csv-parse.js` — bare mid-field quotes now literal, leading UTF-8 BOM stripped
**Dev:** Code review across 17 inputs found two real-world breakages: (1) a stray `"` inside an unquoted field (e.g. `a"b,c`) flipped the parser into quoted mode, silently swallowing the following comma and dropping a column — now a `"` only opens quoted mode when it's the first character of a field (`field === ''`), matching Excel; any other `"` is appended literally. (2) Excel-exported bank CSVs commonly start with a UTF-8 BOM (`﻿`), which was landing inside the first header/field (e.g. `﻿Date`) and would have silently broken Task 3's header detection — now stripped once at the top of `parseCsv` before parsing starts. Also added tests pinning the row-flush guard in the KEEP direction (blank/whitespace-only lines dropped vs. empty-field and quoted-empty-field lines kept), since the existing tests only covered the DROP direction and several wrong guard formulations would have still passed them. Lone-CR (classic Mac) line endings remain an explicit, documented non-goal — noted in a source comment, not handled.
**Plain:** Fixed two edge cases in the CSV reader: a stray quotation mark inside a word no longer eats the next column, and an invisible marker some spreadsheet exports add to the start of a file no longer sneaks into the first cell.
**Why:** Real bank export files have both quirks, and either one would have quietly corrupted a transaction or broken next week's header-detection step in a way that's hard to trace back to this file.

### [2026-08-22 15:45] Added

**Tech:** `lib/csv-parse.js` — character-level CSV parser (`parseCsv(text) → string[][]`)
**Dev:** Hand-rolled state machine instead of `split(',')` because real bank exports quote fields containing commas (e.g. `"COLES, COBURG"`) and escape embedded quotes as `""`. Handles LF and CRLF line endings, drops a trailing newline, and treats a whitespace-only row as empty rather than a one-field row — that last part needed a one-line fix to the reference implementation's row-flush guard, which otherwise let `'   '` slip through as `[['   ']]` instead of `[]`. No headers, types, or date/amount parsing here — that's later modules' job.
**Plain:** Added the code that turns a bank statement CSV's raw text into rows of text fields, without breaking on commas that are part of a shop name.
**Why:** Every later step (matching formats, cleaning up merchant names, importing transactions) depends on getting this first read of the file exactly right, so a shop name like "COLES, COBURG" doesn't get chopped into pieces.
