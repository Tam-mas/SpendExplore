### [2026-08-29 01:30] Fixed

**Tech:** `lib/recurring.js` — new `buildManualSeries(merchant, ordered)`, called from `applyOverrides()` for any forced merchant that `detectRecurring()`'s loose pass still drops (gaps matching no cadence band at all, not just "fewer than 3 occurrences"). Builds a `cadence: 'irregular'` series annualised off the AVERAGE gap between charges instead of a named cadence, with `nextExpected: null` (no cadence means no honest prediction) rather than fabricating one. A single-occurrence forced merchant still renders (`occurrences: 1`) but with `annualCost: 0` — "not enough data" is shown, not guessed at. `web/recurring-view.js` — `row()` renders `nextExpected: null` as `—` instead of the literal string `"null"`. `web/style.css` — added `.drilldown-table button` styling (padding/border/radius matching `.recurring-table button` and `.budgets-table button`), so the new "Mark recurring" button added last session no longer falls back to unstyled browser defaults. Tests: `tests/recurring-routes.test.js` (two new cases reproducing the exact reported gap pattern — 21-day then 29-day — and the single-occurrence case), `tests/recurring-view.test.js` (the `—` rendering).
**Dev:** Root cause: `detectCadence()` only recognises gaps that land in one of five fixed bands (weekly/fortnightly/monthly/quarterly/annual, each ± a tolerance) or a clean double of one. A bill genuinely paid on different days each month can produce a gap that fits NONE of them, and `detectRecurring()`'s per-merchant loop silently `continue`s past any merchant with no matching cadence — so `applyOverrides()`'s forced-merchant re-detection pass, which only lowers the minimum occurrence count, still found nothing and the row never appeared even though the override was correctly persisted to disk. This is why "even on refresh" didn't help: the override was saved, but re-running detection hit the exact same dead end every time. Live-verified with a synthetic 3-transaction fixture reproducing the reported dates/amounts (added and removed from `data-test/ledger.json`, never `data/`): searching, marking recurring, and confirming the merchant appears under "Possibly recurring" with "Irregular" cadence and a `—` in the Next column.
**Plain:** Marking a bill as recurring now works even when it's paid on an irregular schedule (different day each month) — it used to silently do nothing for exactly those bills.
**Why:** the whole point of "Mark recurring" is to catch bills the automatic detector is too conservative to call recurring on its own — but the fix only relaxed HOW MANY times it needed to appear, not WHETHER its timing had to fit a clean pattern, so the messiest, most manually-obvious bills were exactly the ones it still couldn't handle.

(5) `parseAmount('1.404,01')` and `parseAmount('1 404,01')` silently returned values 100x too large (European decimal-comma and space-grouped forms misread as US thousands-grouping); now any comma usage is validated against strict US-style grouping (`\d{1,3}(,\d{3})+` before an optional `.` decimal) and rejected as `null` otherwise. European and space-grouped amount formats remain unsupported by design — the fix is refusing to guess, not adding support.
**Plain:** Fixed five cases where the CSV-format guesser would have gotten it wrong in ways that are hard to notice: picking the running balance instead of the actual transaction amount on credit-card and overdrawn-account exports, missing the header row on layouts that don't start with the date, mislabelling an account name as the transaction description, calling a self-contradictory date column "confident" when it isn't, and silently turning a European-style amount like 1.404,01 into a number 100 times too big instead of refusing to guess.
**Why:** These are exactly the "looks fine until you check the numbers" bugs the whole module exists to prevent — a wrong balance-vs-amount pick or a misread European amount would have quietly fed wrong numbers into every chart, and nobody would think to double-check a number that looks plausible.

### [2026-08-22 16:20] Fixed

**Dev:** Code review across 17 inputs found two real-world breakages: (1) a stray `"` inside an unquoted field (e.g. `a"b,c`) flipped the parser into quoted mode, silently swallowing the following comma and dropping a column — now a `"` only opens quoted mode when it's the first character of a field (`field === ''`), matching Excel; any other `"` is appended literally.
